# AriBotV6 — Discord AI-персонаж Ари (текст + голос)

Полностью локальный стек: Ollama (LLM) + faster-whisper (STT) + Qwen3-TTS CustomVoice
(Ono_Anna) или Silero (TTS, на выбор). В интернет ходит только сам Discord (и разовая
загрузка моделей). Ветка этой версии: `AriBotV6`.

## Что изменилось в версии 6

- Faster Qwen3-TTS с CUDA Graphs, голосом Ono_Anna и настоящим прогревом.
- Полный ответ озвучивается одним вызовом и одной записью. Новый вопрос
  отменяет устаревшую озвучку, включая незавершённый синтез.
- Пометки эмоций внутри ответа передаются в инструкции Qwen с границами
  фрагментов. Точность смены подачи зависит от модели.
- HTML-теги и текстовые имитации вызовов инструментов удаляются перед озвучкой.
- Отдельный VAD для каждого участника; сохраняются начало фразы и паузы,
  во время синтеза бот продолжает принимать голос.
- Обычная самостоятельная реплика через 2 минуты тишины. После 5 минут
  без речи людей — короткая собственная песенка. Реплики бота не сбрасывают
  пятиминутный таймер; напевная подача экспериментальная.
- Пение по команде `ari!sing` / `ari!пой` и по явной голосовой просьбе.
- Атомарное сохранение памяти с блокировками, сжатие истории только после
  успешного ответа, изоляция сводок собеседников и отмена просроченных запросов.
- Логирование подготовки звука и начала/окончания воспроизведения.

Веса, виртуальные окружения, `.env`, память, логи и личные аудиозаписи
не входят в Git. После клонирования их нужно подготовить локально.

## Архитектура

```
config.py     — все настройки (.env)
memory.py     — память о собеседниках (memory.json, авто-сжатие истории)
llm.py        — Ollama: стриминг, персонаж, сжатие истории
stt.py        — faster-whisper, распознавание напрямую из памяти
tts.py        — Qwen CustomVoice (GPU) или Silero (CPU) -> PCM
qwen_backend.py / qwen_worker.py — отдельный постоянный процесс Qwen
speaker.py    — очередь озвучки полных ответов
voice_sink.py — приём голоса, VAD, детекция конца фразы
bot.py        — Discord-команды и склейка
watchdog.py   — перезапускает bot.py, если он завис или упал
```

## Ключевые фичи против старой версии

- **Цельная озвучка**: бот собирает полный ответ модели, синтезирует его
  одним вызовом TTS и воспроизводит одной записью.
- **Ответ по имени**: реагирует только на обращение (WAKE_WORDS, по
  умолчанию «ари»/«ори»/«ария») — остальной разговор рядом просто
  игнорирует, не встревая в чужой диалог
- **Без ffmpeg и временных файлов**: Whisper читает аудио из памяти,
  Silero отдаёт PCM сразу в Discord
- **Команды на лету**: `ari!voice Ono_Anna|Vivian|Serena|Sohee`, `ari!model <имя>`

## Установка (Windows, кратко)

1. Python 3.11/3.12 (НЕ 3.13+: нужен audioop)
2. Ollama + модель: `ollama pull gemma4:e2b`
3. `py -3.11 -m venv venv && venv\Scripts\activate`
4. `pip install torch torchaudio` (для запасного Silero; Qwen работает в отдельном окружении)
5. `pip install -r requirements.txt`
6. Подготовить окружения Qwen по инструкции ниже.
7. `copy .env.example .env`, вписать DISCORD_TOKEN и имя установленной модели Ollama.
8. `python watchdog.py` (рекомендуется — авто-перезапуск при зависании;
   для разовой отладки можно и `python bot.py` напрямую)

Первый запуск Whisper/Silero может скачать модели. Qwen работает с уже
скачанными локальными весами без обращения к облачному TTS.

### Голос Qwen CustomVoice (Ono_Anna)

По умолчанию выбран `TTS_ENGINE=qwen`, `QWEN_SPEAKER=Ono_Anna`.
Бот вызывает отдельный постоянный процесс, который загружает модель один раз,
синтезирует по очереди и возвращает PCM 48 kHz stereo 16-bit. Это позволяет
оставить зависимости бота и Qwen в разных окружениях. Процесс завершается вместе
с ботом, в том числе при аварийном перезапуске через watchdog. Лог: `qwen_tts.log`.

Настройки ускоренного режима:

```env
TTS_ENGINE=qwen
QWEN_SPEAKER=Ono_Anna
QWEN_RUNTIME=faster
QWEN_PYTHON=qwen_tts_trial/faster_env/Scripts/python.exe
QWEN_MODEL_DIR=qwen_tts_trial/weights/custom
QWEN_TIMEOUT_SEC=180
QWEN_MAX_TOKENS=768
```

Для новой установки создайте отдельное окружение Python 3.12, установите
CUDA-сборки torch/torchaudio 2.8.0 и `requirements-qwen.txt`, затем скачайте
`Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice` в `QWEN_MODEL_DIR` целиком, включая
`speech_tokenizer/`. Пути можно изменить через `.env`. Текущую папку
`qwen_tts_trial` удалять нельзя: она содержит активное окружение и веса.

Ускоренный режим использует Faster Qwen3-TTS 0.5.4 и CUDA Graphs, сохраняя
CustomVoice/Ono_Anna, инструкции подачи и единую запись полного ответа.
Перед готовностью выполняется пробный синтез без воспроизведения.
`faster_env` содержит новые библиотеки Transformers 5, а зависимости CUDA/PyTorch
берёт из исходного `env` через `qwen_shared.pth`. Обе папки нужны для работы.
Для повторной установки создайте окружение Python 3.12, добавьте абсолютный
путь `env/Lib/site-packages` в `faster_env/Lib/site-packages/qwen_shared.pth`,
затем установите `requirements-qwen-faster.txt` с `--no-deps` в `faster_env`.
Пример подготовки в PowerShell из корня проекта (после установки Python 3.12):

```powershell
py -3.12 -m venv qwen_tts_trial/env
./qwen_tts_trial/env/Scripts/python.exe -m pip install torch==2.8.0 torchaudio==2.8.0 --index-url https://download.pytorch.org/whl/cu128
./qwen_tts_trial/env/Scripts/python.exe -m pip install -r requirements-qwen.txt transformers==4.57.3
./qwen_tts_trial/env/Scripts/python.exe -c "from huggingface_hub import snapshot_download; snapshot_download('Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice', local_dir='qwen_tts_trial/weights/custom')"
py -3.12 -m venv qwen_tts_trial/faster_env
$sharedPackages = (Resolve-Path 'qwen_tts_trial/env/Lib/site-packages').Path
Set-Content 'qwen_tts_trial/faster_env/Lib/site-packages/qwen_shared.pth' $sharedPackages -Encoding ascii
./qwen_tts_trial/faster_env/Scripts/python.exe -m pip install --no-deps -r requirements-qwen-faster.txt
```

Возврат к обычному движку: `QWEN_RUNTIME=standard` и
`QWEN_PYTHON=qwen_tts_trial/env/Scripts/python.exe` в `.env`.

LLM может добавлять перед предложениями скрытые пометки `[whisper]`, `[amused]`,
`[sigh]`, `[excited]`, `[sad]`. Они превращаются в инструкции CustomVoice,
удаляются из произносимого текста и не сохраняются в истории ответа.
По умолчанию используется обычная разговорная подача. Смех, вздохи и эмоции
зависят от того, как модель выполнит указание, и не гарантируются для каждой фразы.

На RTX 4070 Ti SUPER Faster Qwen после прогрева синтезировал тестовую реплику
за 1,4 с против 8,1 с у обычного движка; длительность аудио 4,3 и 4,2 с.
В проверке через интерфейс бота короткие реплики готовились за 1,0–1,2 с.
Это локальные замеры при выключенном боте, а не гарантия времени любого ответа.
Ollama и Qwen делят видеопамять.
В качестве запасного варианта доступен `TTS_ENGINE=silero` (CPU),
`SILERO_SPEAKER=xenia|baya|kseniya`. F5-TTS удалён.

## Команды

- `@Бот <текст>` — ответ в текстовом чате
- `ari!join` — зайти в ваш голосовой канал и слушать
- `ari!leave` — выйти
- `ari!sing` или `ari!пой` — сочинить и напеть короткую песенку (Qwen)
- Голосом: «Ари, спой песенку», «Ари, напой что-нибудь», «Ари, можешь спеть?»
- `ari!voice [имя]` — показать/сменить голос активного движка (Qwen: Ono_Anna/Vivian/Serena/Sohee)
- `ari!model [имя]` — показать/сменить модель Ollama

## Таймеры, проверка и лог

```env
IDLE_CHATTER_SEC=120
IDLE_SONG_SEC=300
```

При новой речи людей отсчёт начинается заново. Песенка не накладывается
на текущий ответ; при разговоре во время её подготовки она откладывается.
Все изменения `.env` и кода требуют перезапуска бота.

Проверки без запуска Discord и загрузки моделей на GPU:

```powershell
./venv/Scripts/python.exe -m unittest test_voice_sink test_reliability test_qwen_integration -v
```

Просмотр обновляющегося лога:

```powershell
Get-Content ./bot.log -Encoding UTF8 -Tail 30 -Wait
```

`[bot]` — сформированный текст, `[tts start]` / `[tts ready]` — синтез,
`[play start]` / `[play finished]` — воспроизведение. Завершение воспроизведения
подтверждает колбэк Discord, но не качество звука у слушателя.

## Что она умеет делать сама (function calling)

Помимо разговора, модель по ходу диалога может по-настоящему выполнять
действия в Discord (не просто говорить, что сделала — см. `discord_tools.py`,
`llm.py`).

В голосовом канале, где она сейчас сидит:
- Ставить/менять статус канала
- Мьютить/размьючивать участников голосового канала (в том числе саму себя,
  если попросят)
- Перемещать участников в другой голосовой канал или отключать от голоса
- Проигрывать звук со звуковой панели сервера

В текстовом чате, где к ней обратились:
- Закреплять сообщение
- Отправлять TTS-сообщение
- Создавать публичную ветку
- Ставить/убирать реакцию
- Архивировать/закрывать текущую ветку

Модель заранее знает реальные названия голосовых каналов и звуков на панели
сервера (список подставляется в системный промпт) — не угадывает вслепую.
Действия ограничены тем каналом/сообщением, где идёт разговор, а не всем
сервером сразу — например, замьютить можно только того, кто сейчас в одном
канале с ней.

## Известные особенности

- Используется экспериментальная ветка py-cord `fix/voice-rec-2`
  (официальный релиз ещё не поддерживает приём голоса после DAVE).
  Сбой записи при заходе/выходе людей из канала — известный баг ветки,
  бот сам перезапускает запись.
- VAD не отличает вашу речь от музыки/видео на фоне — фоновый звук
  может распознаваться как фразы.
- Для каждого участника используется отдельный VAD. В запись входят
  200 мс перед обнаружением речи, короткие паузы и тихие окончания;
  минимальная длительность проверяется по обнаруженной речи, без тишины.
  Во время синтеза ответа приём продолжается. Если обработчик занят,
  действует прежняя очередь: последняя ожидающая фраза каждого участника.
- **Барж-ина (прервать её на полуслове) нет и не будет, пока это не починят
  выше по стеку**: пока бот говорит, входящий звук вообще не обрабатывается
  (voice_sink.py, is_bot_speaking). Причина — приём и воспроизведение
  одновременно (полный дуплекс) при DAVE-шифровании регулярно ломает
  расшифровку входящего звука в этой ветке py-cord; та же проблема
  воспроизводится и в других библиотеках (discord.js и т.п.) — это
  незрелость поддержки DAVE для приёма звука во всей экосистеме, а не наш
  баг. Слова, сказанные во время её ответа, теряются, а не откладываются.
- Изредка вызов voice-клиента (play/stop/start_recording) зависает насмерть
  на нативном уровне и держит GIL — тогда даже таймауты внутри процесса не
  спасают, замирает всё целиком. `watchdog.py` следит за heartbeat-файлом
  снаружи процесса и перезапускает bot.py, если это случилось — поэтому
  запускать рекомендуется через него, а не напрямую.
